# Share what you learned with AEL

AEL grows when photographers bring back what worked, what failed and what was unclear on their own data.
A short, well-supported lesson can be useful even without a finished image or a code change. Contributions
are optional, and you do not need to publish your photographs.

## What helps

- A measured camera or processing behaviour, with the conditions in which it occurred.
- A clearer instruction or a reproducible bug and its fix.
- A failed approach, a negative control or a limit that saves someone else the same wrong turn.
- A case study that separates the preferred appearance from registration, file integrity and scientific claims.

Start with the problem and the lesson. Include the AEL version or commit and relevant equipment or software,
the steps tried, the checks and results, and what remains uncertain. Separate observations from interpretations.
Keep failed checks visible. Settings from one image are examples, not new defaults for everyone.

If source data stays private, say which results readers cannot reproduce. An aggregate table is useful evidence
but does not make a case independently reproducible. Use a small synthetic example when it demonstrates a bug;
label it as synthetic and do not present it as an astronomical observation.

## With your agent

At the end of a useful stage, your agent should point out a specific lesson that could help another user and
prepare a short local draft. It should show the exact text and attachments, the public destination and your
chosen attribution before asking permission to submit. For example, in your language:

> We found that [observation under stated conditions]. This could help someone using [relevant setup].
> Here is a short summary with the checks and limits. May I publish this to AEL as [an issue / a pull request],
> with the attribution you have chosen?

Approval to work on your photos does not approve an upload. The agent should check the proposed material for
credentials, personal paths, identifying metadata, precise private locations and third-party material.
Photos, RAWs, Photoshop files and private receipts stay local unless you explicitly approve the exact files
for that public contribution. Share only material you have the right to share.

If you decline, the agent continues your work without repeating the invitation for the same lesson. If no
reusable lesson emerged, there is no need to manufacture a contribution. If you already approved the exact
content and destination, the agent can submit within that approval without asking again.

## Where it goes

First check the [existing issues](https://github.com/PeterWar/Agentic-Eclipse-Library/issues) and
[pull requests](https://github.com/PeterWar/Agentic-Eclipse-Library/pulls) for the same finding.

- Open an issue for a report, an unresolved observation or a proposed improvement.
- Open a pull request from your own fork for a concrete documentation or code change. Explain what changed,
  which checks you ran and which you could not run. Documentation checks do not establish image validity.
- If the agent cannot submit to GitHub, keep the draft local and give you the destination and next step.
  It must not claim that a prepared draft has been published.

Issues and pull requests are public. Choose the GitHub identity and attribution you want to use; an anonymous
case description does not hide the account or commit metadata used to submit it. Accepted contributions retain
their authorship and can be linked from the community section of the README.

Only **PeterWar** can update or merge into `main`. A submitted contribution remains a proposal until the
maintainer accepts it. Contributions to the repository use its existing [MIT licence](LICENSE).
