# PixInsight bridge for Agentic Eclipse Library

This connector runs the Agentic Eclipse Library (AEL) from PixInsight, with one menu entry and one dialog. Choose the RAW photos of a total solar eclipse, and optionally their darks and flats: AEL stacks them into one image and opens it here with AEL's default filter layers (NRGF, WOW edge-aware and isotropic ACHF 04) and their PixelMath composite. The engine that does it, `python/ael_auto.py`, is the one the Photoshop connector carries, the same file, so the same photos give the same linear master and the same layers in either program. From an open image, the dialog also makes the `structure` and `polar` images and AEL's filter layers with an adjustable PixelMath composite. It applies AEL's fixed recipes, gates and receipts; it does not make agent decisions and does not change the AEL algorithms.

Your files are never edited. Each resulting image opens in a new PixInsight window and is also written to disk.

## Requirements

- PixInsight 1.9.4 or later.
- Python 3.10 or later with AEL's dependencies: `python -m pip install numpy scipy opencv-python-headless pillow tifffile imageio rawpy exifread`. AEL itself is not on PyPI. `rawpy` reads the RAW photos; `exifread` is optional: without it, AEL cannot name the camera or read fractions of a second in the capture times. No external program is needed.
- **AEL 1.4.0 or later.** The package built by `tools/build_package.py` carries it under `runtime/ael` and the connector uses it with no setting at all. In a source checkout the repository root, which holds `ael/`, is used the same way. An older AEL, or one whose version cannot be read, is refused before anything is processed: 1.4.0 measures the geometry on the image, which the dialog uses, since it asks for no geometry; 1.3.6 has the soft-log and MGN corrections that the structure image and the filter layers depend on, and 1.3.5 the edge-aware WOW and the layer names per family.

### Finding Python

The dialog has no Python field: the connector looks for one by itself, in this order: the path saved by the last successful run, `AEL_PYTHON`, `python3` and `python3.N` (newest first) in the Homebrew and system folders, the virtual environments in `~/.venvs`, `~/.virtualenvs` and `~/venvs` (and `~/venv`, `~/.venv`), pyenv, conda and Apple's `python3`. Each one is probed before it is used: Python 3.10 or later, and `import ael` works with the selected AEL folder, which needs NumPy and the rest. The first that passes is used and saved. If none does, the message says how to install the dependencies and lists every interpreter that was tried and why it failed. A Python without the dependencies is skipped, not used. To use one particular Python, set `AEL_PYTHON` to it. AEL is always the one that comes with the connector (or the repository root in a source checkout).

## Local installation

1. Keep the folder `pixinsight-ael/` together: the scripts, `python/` and `runtime/` with their relative paths.
2. In PixInsight, choose **Script > Feature Scripts…**.
3. Click **Add** (it asks for a folder), choose the folder `pixinsight-ael/`, and the dialog lists `AELBridge.js`, enabled. Click **Done**.
4. Open **Utilities > Agentic Eclipse Library**.

This is a local build for testing, not a signed update repository. `tools/build_package.py --out FOLDER [--zip FILE]` assembles the folder, with `runtime/ael` copied from the checkout and checked byte by byte, `runtime/VERSION.json` (AEL version, the last commit of `ael/`, the commit of the connector and whether either had uncommitted changes, with the same keys as the Photoshop connector's) and the synthetic files of `demo/`.

## Use

The dialog is meant for people who do not know the technology: it asks only for what a person knows, and each operation shows only its own fields.

1. In **Utilities > Agentic Eclipse Library**, choose what to make (**Make**): **Stacked image from RAW photos** (the first one, chosen when the dialog opens), **Structure image**, **Unrolled view of the corona** (a radius field appears: the outer radius in solar radii, 4 by default), or **Filter layers and PixelMath composite**.
2. For a stacked image, **Totality RAW photos — Add files…**: select every RAW photo of the totality (all exposures together; CR2, CR3, NEF, ARW, DNG, RAF, ORF or RW2, several at once). **Darks and flats (optional) — Add files…**: the dark and flat frames of the same camera, if you have them, mixed as they are. A file that is not a RAW photo is not added, and the Process Console says so. For the other three operations, open a monochrome or three-channel RGB image and check it in **Image** (for a floating-point TIFF with values outside 0–1, or one without data in its last sample, see **When PixInsight does not hold the file as it is stored**).
3. The output folder starts at Downloads (then at the last folder used); **Browse…** chooses another. Each run creates a new timestamped subfolder, so previous runs are not overwritten.
4. Click **Run**.

For a stacked image there is nothing else to set: see **Stacked image from RAW photos** below for what AEL works out by itself and what opens. For the other operations there is no geometry to give either. AEL measures it on the image (`ael.geometry.measure_geometry`): it finds the lunar disc, or the closed region without data that AEL stacks leave around the Moon, and places the Sun at its centre with its radius; north, parity and scale stay unknown (position angles are counted from the top of the image). A new window, `AEL_geometry_check_…`, shows the image with that circle drawn in red; the image itself is not changed. The receipt says what was measured and what was assumed. An image without a lunar disc is refused with that reason. A geometry can still be given to AEL from the terminal (`python -m ael structure --geometry FILE.json`) or to `aelBridgeRunOnView` from a script.

For an open image, the bridge writes a 32-bit floating-point, interleaved TIFF in a unique temporary directory. A preflight check rejects planar RGB, unexpected shapes, incorrect sample types and missing ICC data before AEL runs. If PixInsight changes ICC header flags while writing TIFF, the helper restores the original profile and verifies that every image sample remains unchanged. The receipt records this repair. The temporary directory is removed afterwards.

The output folder of a structure image or an unrolled view contains the AEL products, `input_geometry.json` and `AEL_BRIDGE_RECEIPT.json`. The bridge receipt records the command, Python and AEL paths and versions, input TIFF SHA-256, layout, ICC information, files and gate result. `structure` also writes AEL's own `structure_RECEIPT.json`; because `polar` does not currently write an AEL receipt, the bridge receipt is the run record for that command. Receipts are printed to the Process Console.

## Validation

The tests and tools are in the repository (`plugins/pixinsight-ael/tests` and `tools`); the delivered package does not carry them.

The test launcher looks for an interpreter in the same places as the dialog (see **Finding Python**); `AEL_PYTHON` selects one explicitly. It uses synthetic data, and the RAW photos of a totality when they are given (`--raw`, a text file with one path per line, and `--calibration` for their darks and flats): there are no synthetic RAW files. The tests start new PixInsight instances with `-n --automation-mode` and `--force-exit`, which never send a script to an instance that is already open (without `-n`, PixInsight yields the command to a running instance). A test that is stopped by its timeout stops only its own instance. On Apple silicon PixInsight 1.9.4 has only the V8 JavaScript engine: every script must start with `#engine v8`, or PixInsight refuses it (*the legacy 'sm' JavaScript engine is not available in this PixInsight build*), and in automation mode that error is never seen outside the instance. The connector's scripts and the test scripts carry the line.

```bash
PYTHONDONTWRITEBYTECODE=1 python plugins/pixinsight-ael/tests/run_tests.py \
  --output /path/to/validation-output [--raw raws.txt --calibration calibration.txt]
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=. python plugins/pixinsight-ael/tests/dialog_flow.py \
  --repo . --python "$(which python)" --raw raws.txt [--calibration calibration.txt] \
  --output /path/to/dialog-output
PYTHONDONTWRITEBYTECODE=1 python plugins/pixinsight-ael/tests/entry_scripts.py \
  --repo . --output /path/to/entry-output
```

`run_tests.py` covers:

- exact float32 RGB and monochrome TIFF round trips, shape and orientation;
- negative orientation tests;
- exact ICC preservation from a source TIFF;
- identical output pixels from direct AEL and bridge executions of both commands;
- unchanged source pixels;
- clear errors for a missing executable, missing AEL, an old Python and an old AEL (1.3.3, 1.3.6 and an unreadable version are refused, 1.10.0 is accepted: versions compare as numbers);
- the interpreter detection with nothing chosen, from a clean saved-settings state and without `AEL_PYTHON`;
- paths containing spaces and accented characters;
- samples without data (NaN): the file PixInsight's writer makes has them as 1.0 (the control), the file the bridge hands to AEL has them as NaN again, and the structure image of a scene with a band, a block and a patch without data equals the one `python -m ael` makes from the file, while AEL on the file as PixInsight writes it gives three different images;
- a file with values outside 0–1 (which PixInsight rescales) and a file whose last sample is NaN (which it reads as black): the bridge runs AEL on the file itself, its structure image equals the one `python -m ael` makes from the file, and the file is left as it was;
- dialog and result images rendered by PixInsight.

`dialog_flow.py` builds the dialog in PixInsight, chooses each of its four operations, fills its few fields, presses **Run** and checks the windows and files each one leaves. The file and folder choosers are replaced by stand-ins that record how the dialog asks (several files at once, RAW photos only, in lower and upper case) and answer with the files a person would pick; a message box is recorded instead of shown. For the stacked image: the photos are added twice and a TIFF with them, the darks and flats mixed in the second list; the photos are listed once and the TIFF is not added; the linear master and the seven layer images equal those of the same engine run from the terminal with the same files (`python/ael_bridge_check.py raw`); the PixelMath composite matches AEL's own composite (its preview) within one 8-bit step; a master dark is made for each exposure and a master flat; every photo is stacked; the geometry is measured on the RAW files and a check window opens; the engine's steps reach the Process Console; and the closing message, word for word the Photoshop connector's, appears in a message box and in the Console. Without photos, **Run** says what is missing; a run stopped the way the Console's abort stops it ends with a message, opens nothing and leaves no folder behind. For the other operations: the pixels against `python -m ael ... --geometry auto` and against the workflow helper run from the terminal on the same files, the PixelMath composite, the geometry measured, the Moon of the demonstration image found within 1 px (the centre on both images, the radius on the linear one) and a check window opened, and the filter layers of an image PixInsight rescaled made from its file. It also checks that the stacked image is the operation chosen when the dialog opens, that each operation shows only its own fields, and that the output folder starts at Downloads and **Browse…** sets it (the folder the dialog keeps is restored afterwards).

`entry_scripts.py` runs `AELBridge.js`, the file that the Script menu starts, unchanged in its own new PixInsight instance, and checks that the dialog appears with its title, its Run button, its fields and four operations (the stacked image from RAW photos chosen, with its lists shown), an output folder that exists (or Downloads), none of the fields of earlier versions (Python, AEL folder, geometry, camera profile, one dark, one flat) and the AEL folder that comes with the connector, then closes it with Cancel. The same check on a copy whose bridge entry has lost the include of its dialog fails (`ReferenceError: AELBridgeDialog is not defined`), so a broken entry file cannot pass. For a built package: `--plugin PACKAGE/pixinsight-ael --expect-root PACKAGE/pixinsight-ael/runtime`.

`VALIDATION.json` contains the gates and exact commands. A missing PixInsight executable or a failed gate makes the complete validation fail. `--skip-pixinsight` runs only direct AEL checks and is not a complete bridge validation. `--skip-captures` omits only the visual captures.

### Size and memory

`structure` was run through the bridge on a synthetic corona of 7,506 × 10,551 pixels (80 million, the size of the 2026 composites): 49 s from the click to the three result windows on an Apple-silicon Mac with 64 GB, and the three outputs equal those of `python -m ael` on the same file bit by bit (SHA-256). The peak was **30 GB of memory** (PixInsight with the image, plus the Python process that runs AEL; the terminal run alone peaks at 29 GB), so plan on that for images of this size. The filter workflow was not run at that size.

### When PixInsight does not hold the file as it is stored

PixInsight does not always read a floating-point TIFF faithfully. A file with values outside 0–1 is rescaled to exactly 0–1, `(x − min) / (max − min)`, so the view holds numbers that are not in the file; and a file whose last sample is NaN (no data in the bottom-right corner, which a registered stack often has) is read as a completely black image, with no message. AEL does not give the same result on those numbers (its structure image depends on the scale and on the zero: a plain ×0.5 changes 30,924 of the 786,816 samples of a test image).

A view that is still its file (not processed since it was opened) is therefore compared with it before anything is exported: the size, the count of samples with and without data, the smallest and largest value and the sum of the finite values must agree, and the file must not leave 0–1. If they do not, the bridge runs AEL on the file itself, as `python -m ael` reads it. It says so in the Process Console, and the receipt records the file, its SHA-256 and the reasons (`source.ael_input`, `source.file_reasons`, `input_file`). The file is never written or removed. An AEL stack (a `linear.tif` with values far above 1 and NaN outside its coverage) can thus be opened as it is, and the result is the one `python -m ael` gives on that file, which the tests check pixel by pixel. A view that has been processed since it was opened is exported, so AEL gets what you see. Only TIFF files are compared; an image from another format is exported. The filter layers take the image in the same way. The stacked image is not affected: AEL reads the RAW photos from Python.

### Pixels without data (NaN)

AEL marks a pixel without data as NaN, and every stack that AEL writes has them outside its coverage. PixInsight keeps a NaN in the view but writes it to a TIFF as 1.0, so AEL would read a bright area where the file has none: on a real stack of 12 million pixels with 253,851 NaN samples, every sample of the three structure images differed from those that `python -m ael` makes from the file. The bridge therefore reads the positions of the view's non-finite samples and gives them to the helper, which puts them back as NaN in the temporary TIFF before AEL runs. The bridge receipt records how many there were and that PixInsight had written them as 1.0. With this, the same stack gives three structure images equal, sample by sample, to those of `python -m ael` on the file. Infinities are put back as NaN too (AEL takes both as no data).

## Stacked image from RAW photos, and filter layers

The same dialog does both. `AELWorkflowCore.jsh`, `python/ael_workflow.py` and `python/ael_auto.py` go beside the other files.

### Stacked image from RAW photos

Choose **Stacked image from RAW photos**, add the photos (and the darks and flats, if there are any) and click **Run**. The Process Console shows each step as AEL takes it: reading the files, combining the darks and flats, finding the Moon, registering on the Sun, measuring the light of each photo, stacking, the filters. Aborting the script from the Process Console asks AEL to stop at its next step, and a run that stops leaves no folder behind (the test stops a run the way the abort does; the click itself has not been tested automatically).

When it finishes, new windows open: the linear master (`AEL_LINEAR_MASTER`, 32-bit float, no data = NaN), the display base (`AEL_DISPLAY`), the layers and their alphas (`AEL_L_…`, `AEL_A_…`), the PixelMath composite (`AEL_COMPOSITE_…`) and a check window with the circles AEL measured (`AEL_geometry_check_…`: the Sun, and the band the Moon swept, which enters no filter). A message, the same as the Photoshop connector's closing message and also written to the Process Console, says how many photos were stacked, which were left out and why, and where everything was saved: a new folder in the output folder, named with the local date and time as the Photoshop connector names its own (`AEL_YYYYMMDD_HHMMSS_…`), with the linear master (TIFF), `layers/` (the display base, the layers and the alphas as TIFF), `PIXELMATH.md` with the expressions, a preview, `AEL receipt.json` and the recipes in `details/`.

The engine, `python/ael_auto.py`, is the same file in the Photoshop connector (`tools/check_connectors.py` keeps the two copies identical): everything before the filter layers is the same in both programs, and the same photos give the same linear master. Photoshop receives one layered PSB; PixInsight the same layers as images, and the PixelMath expressions that compose them. What AEL works out by itself:

- **Which photos are totality frames.** A photo is a totality frame when AEL finds the dark lunar disc with a bright ring around it, or, in a long exposure whose lunar disc is saturated by scattered light, when its corona registers on the reference. Partial phases are left out. Photos where the photosphere shows (Baily's beads, the diamond ring) are left out too: they saturate beside the lunar limb, within 90° of position angle, at exposures so short that it takes more than twice the brightest light any clean photo shows there. So are photos whose light does not follow the others (a photometric gain beyond 2×, or more than 20 % scatter around the common corona): sunlight scattered near a contact, or a cloud.
- **One pointing.** A mount re-pointed during the totality leaves photos covering another part of the sky; where their edges cross the image the filters would draw that edge. Only the pointing of the reference photo is stacked (a jump of more than 2 % of the sensor's diagonal between consecutive photos starts another pointing; a drift does not), and the other photos are listed as left out.
- **One camera, one ISO.** If photos of several cameras or ISO values are chosen, the camera and ISO with the most photos are used and the others are listed as left out. Each optic needs its own distortion model before images of two optics can be fused, so they are never mixed.
- **Darks and flats.** Each calibration file is classified as a dark or a flat from its preview, then checked on its raw data. Darks are combined by exposure (median, up to 32 per exposure) and each photo gets the dark of its exposure and ISO; a photo without one is calibrated with the black level. Flats are combined with AEL's master flat (each Bayer plane normalised, up to 48 frames).
- **Black and saturation levels.** The black level is the mean level of the masked border of the sensor when the file has one (LibRaw does not know every camera: for the Canon EOS R6 Mark III it declares 0–97 where the sensor reads 512.2), otherwise LibRaw's. The saturation level is the plateau where the sensor clips. The top 15 % of each RAW range is not used, because some sensors stop being linear well before they clip; the shorter exposures cover it.
- **The registration on the Sun.** The corona is fixed on the Sun and the Moon moves across it. Each photo is registered on the corona of a reference photo: a band-pass of the logarithm of the corona between 1.36 and 3 solar radii (saturated pixels, the photo's own Moon and pixels without data left out), first by cross-correlation and then by Gauss-Newton for a shift and a turn of the field about the Sun (a mount that does not follow the sky turns the field during the totality). Two checks: the result must not depend on its starting point, and the coronal structure must match better than the same photo turned by 90° and 270°. A long focal length is registered at a reduced scale, where the Sun is about 240 pixels across its radius. The lunar limb of every photo is measured to about a tenth of a pixel. Over a totality the Moon's motion against the Sun is a straight line in time, so that line is fitted on the photos registered on the corona, the turn of the field is fitted as a straight line in time too, and every photo is placed by its own lunar limb minus the line. A photo that the corona places far from the line is left out. When the Moon and the corona disagree by more than a pixel on that line, or the line is faster than the Moon can cross the Sun (0.65″ a second for a Moon at least 944″ in radius: wrong capture times, or a corona registration that slipped), the data cannot tell which is biased: each photo registered on the corona keeps its own registration, and a photo without one stays out, with the reason in the receipt. Without capture times, or with fewer than three photos on the corona, the corona registration is used as it is.
- **One sky for all photos.** Thin clouds or haze can change the light during a totality, and exposure times are not exact. AEL measures one photometric gain per photo where it and the others have good unsaturated data (a coarse grid of radius and position angle around the Sun, through each photo's final placement, fitted by alternating medians with the reference fixed). What the gains leave unexplained is the sky's consistency. Above 3 %, the sky changed: the gains go to the stack (`flux_scale`) and the Process Console says so. Under a clear sky the nominal exposure times are kept: there the gain fit carries more bias of its own (the blur of the inner corona, the faint sky of the long exposures) than the shutter carries error. In both cases each photo's weight fades over the top half of its range instead of the top fifth: two exposures never agree exactly where the longer one saturates, and an abrupt hand-over would leave a step that the filters draw as a ring.
- **The Sun.** The Sun's centre is the Moon's centre at the middle of the photos, on the fitted lunar motion (when that motion does not hold, the Moon's centre of the reference photo). That is exact when the photos span the totality symmetrically and the site is on the central line; elsewhere the true centre is off by up to the difference of the radii, sideways to the Moon's motion. The Sun's radius is the lunar radius over the eclipse's ratio of apparent diameters (a table of total eclipses from 2008 to 2035); when the camera's date matches no eclipse of the table, the lunar radius is used. North, parity and plate scale are not known.
- **Colour.** The camera's daylight white balance and its camera-to-sRGB matrix, derived from the colour matrix LibRaw holds for the camera. The corona keeps the colour that a camera set to daylight records: nothing is neutralised. The matrix is the one of the camera as it left the factory: a camera modified for astronomy (its infrared filter replaced) comes out reddish, and its colour has to be set by hand in PixInsight.
- **The filters.** AEL's default layers with AEL's default opacities, over a display base scaled on the corona between 1.1 and 2 solar radii. The band that the Moon swept across the corona during the photos enters no filter: there the stack mixes different photos.

`tests/dialog_flow.py` makes a stacked image in PixInsight from the RAW photos it is given (see **Validation**). With six Canon EOS R6 Mark III photos of the 2026 eclipse (1/30 s to 2 s), 16 darks and 5 flats, the dialog's linear master and layer images equal, pixel by pixel, those of the engine run from the terminal with the same files. The same six photos without darks and flats give the Photoshop connector the same linear master, byte for byte.

### Filter layers of the active image — validated

Choose **Filter layers and PixelMath composite**, check the image (a linear stack: an AEL `linear.tif`, or a TIFF or FITS file from any program; an alpha channel marks the observed pixels), and click **Run**. Nothing else is asked: the PixelMath composite is always built. The image is handed to AEL as for the structure image (or AEL reads its file, when PixInsight does not hold it as stored); AEL measures the geometry on it and a window shows its circle. The helper measures a display scale from observed corona pixels and generates all sixteen portable AEL filters by default (the box **All 16 filters** unticked makes only AEL's default layers, read from `ael.filterbank.DEFAULTS`: NRGF, the edge-aware WOW and ACHF 04). From the terminal, the helper also takes an AEL `linear.npy` with `geometry.json`, `valid.npy`, `coverage.npy` and `alpha.npy` beside it. It writes:

- float NPY layers and alpha arrays from AEL;
- separate 16-bit TIFF views `AEL_L_<filter>` and `AEL_A_<filter>`;
- `AEL_DISPLAY`, the display base over black with its alpha as a 32-bit float image, which is exactly where AEL starts its own composite, and an independent `AEL_COMPOSITE` duplicate;
- `pixelmath.json` and `PIXELMATH.md` with the expressions, which name the layer and alpha views directly (PixelMath symbols accept constants only);
- AEL and workflow receipts.

The default composite applies NRGF, the edge-aware WOW and isotropic ACHF 04 with their documented opacities, rounded to 8 bits as AEL and Photoshop store them. (Up to AEL 1.3.4 the default WOW layer was the bilateral one; `wow_bilateral` is still accepted as a name for the edge-aware WOW.) The other filters remain separate for manual use. PixelMath touches only the composite, never the display base or linear master, and a PixelMath run that fails stops the workflow. The synthetic validation starts from the display base and compares the PixelMath result with AEL's own composite (`ael/display.tif`); it also checks that the two starting images differ, so a PixelMath that changes nothing cannot pass. AEL composites in floating point from the 16-bit layer images and alpha and rounds once, at the end; the replay starts from the same float32 and so differs from `display.tif` only by that final rounding: 0.50 of a 16-bit step measured, gate one step. A layer with the wrong opacity (one 8-bit step) or the wrong blend mode, built in PixInsight, differs by about 150 and about 11,000 steps and fails the gate.

### The previous linear master

The linear master of earlier versions (`run_master` in `python/ael_workflow.py`, the helper's `master` operation, which also took TIFF and FITS frames) is no longer in the dialog. It stays in that file, with its tests (`tests/workflow_synthetic.py`, `workflow_lunar_motion.py`, `workflow_lunar_noise.py`, `workflow_calibration.py` and `workflow_dark_guard.py`), until both connectors drop it together. Its registration and the engine's were compared on the same real photos with one judge: see **Limitations**.

## Limitations

- **The stacked image has been tried on two eclipses.** So far the engine has been tried on the totality photos of two eclipses, 2024 and 2026, taken with five cameras. It is meant for any total eclipse and should work for others, but both connectors still have to be tried on photos of more eclipses.
- **The registration on the Sun, on real photos.** Judged by the Moon's straight path across the Sun (each photo's lunar limb minus its corona registration, a robust straight line in time on each axis), the photos the corona registers lie within 0.55–0.72 px (rms) of that path on 15 photos of 2026 and 15 and 13 photos of 2024, single photos up to 1.4 px off. On the 2026 photos the lunar velocity came out 4 % faster than the ephemeris (0.282 against 0.271 px/s), which moves the photos at the ends of the minute and a half they span by about half a pixel. The previous linear master, on the same photos and with the same judge, gave 0.40–0.72 px (at most 1.1 px) and the ephemeris velocity.
- **Wrong capture times leave photos out.** The photos the corona cannot register (the shortest exposures) are placed by their lunar limb and the Moon's motion in time. With the capture times of the same photos shuffled, the Moon and the corona no longer make one straight motion: the engine places each photo by its own corona registration and leaves out those without one (8 of 13 photos of 2026, 5 of 15 and 1 of 13 of 2024), and the photos it keeps land within 1.1–1.6 px of where the true times put them. The previous linear master refused all three sets.
- For the operations on an open image, the geometry measured on the image places the Sun at the centre of the measured circle, with its radius. On a single frame that circle is the Moon, and the true Sun can be off by up to the difference of the radii (29 px on the 2026 frames); its radius is the Moon's, 3–8 % larger than the Sun's. Type the Sun's values when you know them. The detection was measured on real stacks and RAW frames of 2024 and 2026 and on 660 synthetic eclipses; it misses some Moons of 25 px radius (wide-angle frames) and every frame whose lunar disc is saturated. Measure it on the linear image when you can: on an image stretched for display the limb comes out inside the true one (62.1 px instead of 63.6 px on the demonstration image, against 63.35 px on its linear version), while the centre stays within 0.02 px.
- Tested only on macOS (Apple silicon) with PixInsight 1.9.4 and AEL 1.4.0. Windows and Linux have not been tested; the interpreter search lists Unix-style folders.
- Python must be installed separately (the package carries AEL, not Python or its dependencies); this is not a native C++ module.
- `structure` and `polar` are covered by the original bridge; the filter layers of an open image are validated with synthetic data.
- A stacked image keeps one photo at a time, plus the stack: with 24–42 megapixel cameras, plan for 8–16 GB of free memory and 1–3 minutes per 10 photos, plus a few minutes for the filter layers.
- ICC profiles are read from the source file and copied unchanged to the temporary TIFF. An unsaved image, or a profile assigned only in memory after reading the file, cannot be verified or preserved reliably by this prototype. The receipt records the ICC origin and byte counts.
- `polar` expects display-range data in [0, 1]. `structure` expects a linear composite with valid geometry and enough outer field for its sky model.
- The connector has not been signed or packaged for automatic updates.
